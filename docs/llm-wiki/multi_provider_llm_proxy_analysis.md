# 멀티 LLM API 공급자 지원을 위한 프록시(liteLLM 등) 대안 분석 보고서

이 보고서는 외부 API 통신 경로를 `z.ai` 단일 대상에서 OpenAI, Anthropic, Gemini 등 다양한 멀티 LLM 공급자로 유연하게 전환하기 위해 **LLM Gateway/Proxy**를 도입하는 방안을 분석합니다. 특히 사용자가 제안한 **liteLLM**의 적합성과 주요 대안들을 비교합니다.

---

## 1. 아키텍처 내 LLM Proxy의 역할

워커 노드들과 오케스트레이터 사이에 **LLM Proxy**가 배치되면, 시스템의 통신 흐름은 다음과 같이 통일됩니다.

```
                      ┌───────────────────────────────────────┐
                      │            LLM API Proxy              │
[Worker 01] ──┐       │  1. Incoming: OpenAI API 규격 수신     │       ┌──► OpenAI
[Worker 02] ──┼──────►│  2. Key Mapping & Auth 주입            ├───────┼──► Anthropic (Claude)
[Worker 03] ──┘       │  3. Outgoing: 대상 API 포맷으로 번역    │       ├──► Gemini
                      │  4. Load Balancing & Failover         │       └──► z.ai (GLM)
                      └───────────────────────────────────────┘
```

워커 노드들은 어떤 모델을 호출하든 상관없이 항상 표준화된 **OpenAI API 스펙(SDK)**을 대상으로 통신을 보내고, 프록시가 이를 대상 공급업체 포맷으로 번역하여 라우팅합니다.

---

## 2. liteLLM 도입 분석

### 2.1 장점 (Pros)
* **압도적인 공급자 지원 (100+ Providers)**: OpenAI, Anthropic, Vertex AI (Gemini), Azure, Cohere, Ollama 및 중국계 LLM(Zhipu/z.ai)까지 현존하는 거의 모든 API를 단일 규격으로 상호 전환해 줍니다.
* **OpenAI 규격 완벽 호환**: 프록시 엔드포인트 자체가 완벽한 OpenAI 규격이므로, 워커의 `grok agent` 또는 타 코딩 도구 설정을 변경할 필요가 없습니다.
* **강력한 운영 기능 내장**:
  * **API 키 및 예산 관리**: 프록시 단에서 하위 API 키를 발급하고, 토큰/달러 단위로 사용자/워커별 예산(Budget) 한도를 설정할 수 있습니다.
  * **로드 밸런싱 & 폴백(Failover)**: 특정 API(예: z.ai)가 먹통이 되면 자동으로 Anthropic이나 OpenAI 모델로 스위칭(Fallback)하게 설정할 수 있습니다.
  * **사용량 모니터링 Dashboard**: 웹 UI를 통해 실시간 토큰 사용량과 비용 청구 현황을 비주얼 대시보드로 모니터링할 수 있습니다.

### 2.2 단점 (Cons)
* **Python 런타임 오버헤드**: Python(FastAPI) 기반으로 작동하므로 Rust나 Go 기반 솔루션에 비해 응답 지연(TTFT - Time to First Token) 및 대량 동시 요청 시 메모리 점유율이 큽니다.
* **추가 인프라 종속성**: 프로덕션 환경의 완전한 기능(속도 제한, 로깅, 토큰 관리 등)을 사용하려면 **Redis** 및 **PostgreSQL** 데이터베이스를 추가로 설치하고 연동해야 하므로 인프라 관리 리소스가 증가합니다.

## 3. 다른 대안 (Alternative Proposals)

### 대안 A: One API (또는 New API) — Go 기반 초경량 게이트웨이
중국 개발자 커뮤니티에서 주도하여 개발된 오픈소스 **Go 기반의 멀티 LLM 라우팅 및 계정 관리 시스템**입니다. 

* **장점**:
  * **초경량/고성능**: Go 언어로 작성되어 단일 바이너리(Docker 한 줄 실행 가능)로 구동되며 CPU와 메모리 사용량이 극도로 낮습니다.
  * **중국계 LLM 완벽 지원**: Zhipu AI(z.ai), Baidu Yiyan, Alibaba Tongyi Qianwen 등 로컬/아시아계 API 지원도가 매우 높습니다.
  * **직관적인 한글/영문 웹 UI**: 채널(공급업체 키) 등록, 사용자 토큰 관리, 충전(Quota) 및 모니터링을 즉시 설정할 수 있는 고성능 대시보드를 제공합니다.
* **단점**:
  * 마이너 공급업체 통합 플러그인은 liteLLM에 비해 다소 부족하지만, 메이저(OpenAI, Claude, Gemini, Zhipu)는 완벽히 커버합니다.

### 대안 B: Portkey / Langfuse Gateway
AI 애플리케이션 운영(LLMOps)과 모니터링에 특화된 엔터프라이즈급 오픈소스 API 게이트웨이입니다.

* **장점**:
  * **모니터링 및 가드레일**: 프롬프트 로깅, 비용 추적, PII(개인정보) 필터링, Fallback, 캐싱 성능이 업계 표준 수준으로 정밀합니다.
  * Node.js/TypeScript 기반으로 준수한 성능을 보여줍니다.
* **단점**:
  * 단순 API 라우팅에 비해 모니터링 기능 위주라 설정과 구조가 무거울 수 있습니다.

### 대안 C: Custom Rust LLM Proxy (자체 내장)
현재 `grok-fleet-orchestrator`는 Rust 기반이므로, 오케스트레이터 내부(`fleet-api`)에 가벼운 HTTP 라우터 모듈을 내장하여 `OpenAI 규격 -> z.ai 규격` 포워딩을 직접 처리하는 방식입니다.

* **장점**:
  * 외부 프로세스나 새로운 컨테이너(Python, Go 등)를 띄울 필요가 없어 아키텍처가 극히 단순해집니다.
* **단점**:
  * 새로운 API 제공자가 추가되거나 제공자의 API 스펙이 변경될 때마다 직접 Rust 코드를 수정하고 빌드/배포해야 하므로 유지보수 비용이 큽니다.

## 4. 비교 분석 요약

| 비교 항목 | liteLLM (Python) | One API (Go) | Custom Rust Router |
| :--- | :--- | :--- | :--- |
| **언어/성능** | Python (무거움, 오버헤드 있음) | **Go (가벼움, 고성능)** | **Rust (최상의 성능)** |
| **인프라 복잡도** | 🔴 높음 (Redis, PG 필수) | 🟢 낮음 (SQLite/MySQL 내장 가능)| 🟢 없음 (바이너리 내장) |
| **공급자 커버리지**| 🟢 최상 (100+ 개사) | 🟡 보통 (주요 20+ 개사) | 🔴 낮음 (자체 코딩 필요) |
| **부가 기능** | 🟢 최상 (비용 제어, 팀 관리) | 🟢 최상 (Quota 충전, 대시보드)| 🔴 없음 (기본 라우팅만) |
| **유지보수 비용** | 🟢 매우 낮음 (커뮤니티 업데이트) | 🟢 낮음 (커뮤니티 업데이트) | 🔴 매우 높음 (직접 유지보수) |

## 5. 최종 아키텍처 권장안

인프라의 복잡도와 성능 효율성을 고려할 때 다음과 같은 단계적 도입을 추천합니다.

1. **운영 복잡도를 최소화하면서 고성능 멀티 API 라우팅이 필요한 경우 (추천)**:
   * **`One API`**를 Docker로 구동하는 것을 추천합니다. `db.internal`을 Postgres와 함께 묶어 경량 컨테이너 하나만 추가하면, CPU/메모리 부하 없이 완벽한 멀티 API 분배 및 z.ai, OpenAI, Anthropic 키 관리를 UI 상에서 간편하게 처리할 수 있습니다.
   
2. **다양한 마이너 모델 사용 및 정교한 예산(Budget) 한도 제어가 필요한 경우**:
   * **`liteLLM Proxy`**를 도입하되, Redis와 PostgreSQL을 결합하여 고가용성 구조로 배포합니다.
