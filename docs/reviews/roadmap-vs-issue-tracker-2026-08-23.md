# Roadmap 원장과 Issue Tracker의 소유권 비교

> 질문: `docs/roadmap/roadmap.md`가 소유한 영구 ID 원장을 Issue tracker가 대체해야 하는가?
> [Issue 추적](../architecture/issues.md)의 "미결" 절이 이 문서를 기다린다.

## 1. 현재 자산 실측

| 항목 | 값 |
|---|---|
| 파일 크기 | 194행 / 41KB |
| 행 수 | 93 (활성 `#48`~`#93` 46행, 보존 레지스트리 `#1`~`#47` 47행) |
| 행 길이 | 중앙값 104자, **최대 2,506자** |
| 정본 링크를 가진 행 | 41 |
| `이 행`을 정본으로 삼는 행 | 7 |
| 이 파일을 건드린 커밋 | 73 |
| 기록된 상태 회귀 사고 | 3 (`docs/log.md` 2026-08-20 ×2, 08-22 ×1) |

표가 **두 개**이고 스키마가 다르다. 활성 표는 `ID·항목·우선순위/상태·정본·완료 게이트`,
보존 레지스트리는 `ID·항목·종결 상태·대표 근거`다.

## 2. 현재 형식이 실제로 겪는 문제

### 2.1 동시 편집 회귀 (3회 발생)

세 번 모두 여러 에이전트가 같은 파일을 순차 편집하는 과정에서 발생했다. 1·2차는
"checkout-HEAD → 편집 → stage → WIP 복원" 절차 중 스냅샷이 앞선 커밋의 완료 기록을 덮었고,
3차는 워킹트리 전체가 `df0be43` 시점 스냅샷으로 되돌아가 7개 행이 후퇴하고 `#72`가 소실됐다.

**행 단위 갱신이었다면 발생하지 않았을 사고다.** 파일 전체를 다시 쓰는 편집 단위가 원인이다.

### 2.2 감사 부재

roadmap.md를 고치는 데 필요한 권한은 **파일 쓰기 권한뿐**이다. capability 검사도, 누가 왜
`#71`을 완료에서 대기로 되돌렸는지에 대한 구조화된 기록도 없다. git 이력이 유일한 증적이며,
3차 사고처럼 스냅샷 되돌림이면 git 이력조차 "누군가 일괄 수정"으로만 보인다.

### 2.3 행이 설계 문서가 되어간다

최대 행이 2,506자다. 문서 정책은 "특정 시점의 테스트 개수, 상세 회고와 설계 개정 횟수는
누적하지 않는다"고 정하고, 갱신 규약은 "계약이나 범위 변경은 설계 정본을 먼저 수정한 뒤 이
문서의 순서·게이트만 동기화한다"고 정한다. 그런데 현재 형식은 긴 산문을 셀 안에 넣는 것을
막지 못하고, 7개 행은 아예 `이 행`을 정본으로 선언한다. **정책은 이미 옳고 형식이 그것을
강제하지 못한다.**

### 2.4 현재 형식이 잘하는 것

무시하면 안 되는 강점이 있다.

- **오프라인·git에서 읽힌다.** 장애 복구 중 계획을 보려면 DB가 살아 있지 않아도 된다.
- **diff로 리뷰된다.** 완료 게이트 문구 변경이 커밋 diff에 그대로 드러난다.
- **절 산문이 순서 근거를 담는다.** `#77`~`#85`, `#86`~`#93` 절 서두의 "왜 이 순서인가"는
  행 데이터가 아니며 표에 넣을 자리가 없다.
- **부트스트랩 문제가 없다.** `#88`·`#93`은 트래커를 만드는 작업 자체다.

## 3. 세 가지 모델

### Model A — Tracker가 원장을 대체한다

영구 ID·상태·게이트를 DB가 소유하고 roadmap.md는 폐기하거나 링크만 남긴다.

| | |
|---|---|
| 해소 | 동시 편집 회귀, 감사 부재, 조회·필터, Agent claim 대상이 실제 계획 항목이 됨 |
| 대가 | 절 산문(순서 근거)의 집이 사라진다. diff 리뷰 surface를 잃는다. **DB 장애 시 계획이 보이지 않는다** — 하필 복구 작업 중에. 93행 + 41개 정본 링크 이주. `#88`·`#93`을 트래커 안에서 관리할 수 없는 부트스트랩 공백 |

### Model B — 분리한다

roadmap.md는 계획 정본으로 남고, 트래커는 더 작은 실무 단위(버그, 개선, Agent가 발견한 선행 작업)를 다룬다.

| | |
|---|---|
| 해소 | Agent claim이 즉시 성립. 계획 정본을 건드리지 않음. 이주 비용 0 |
| 대가 | **회귀 문제가 해소되지 않는다** — roadmap.md는 계속 손으로 편집된다. 두 곳을 봐야 하고, 어느 것이 "진짜 할 일"인지 경계가 흐려진다. 큰 항목과 작은 항목의 기준을 사람이 매번 판단해야 한다 |

### Model C — Tracker가 상태를 소유하고 roadmap.md는 생성물이다

ID·상태·게이트·정본 링크는 DB가 소유한다. roadmap.md는 DB에서 **렌더링해 git에 커밋**하며
아무도 손으로 고치지 않는다. 절 산문은 별도 입력(템플릿 또는 짧은 설계 문서)에서 온다.

| | |
|---|---|
| 해소 | 동시 편집 회귀(행 단위 CAS), 감사(capability + audit event), 조회, Agent claim, **그리고 오프라인 가시성과 diff 리뷰가 그대로 유지된다** |
| 대가 | 생성 파이프라인이 필요하다. 단방향 규율(생성 파일을 손으로 고치지 않기)을 지켜야 한다. 부트스트랩 공백은 남는다 — 초기 항목은 손으로 시딩 |

## 4. 결정적 논점

**정책은 이미 Model C를 요구한다.** 갱신 규약이 "설계 정본을 먼저 수정한 뒤 이 문서의 순서·게이트만
동기화한다"고 정한 순간, roadmap 행의 역할은 **포인터와 게이트**이지 설계 문서가 아니다. 2,506자
행과 `이 행` 정본 7건은 형식이 정책을 강제하지 못해 생긴 드리프트다. 구조화된 저장은 그 드리프트를
구조적으로 막는다 — 정본 링크가 필수 필드가 되면 `이 행`이 성립하지 않는다.

**Model A의 치명적 약점은 DB 장애 시 계획 상실이다.** 이 프로젝트는 Cold Standby가 수동 승격이고
(`#63` 미구현), 백업 복원 절차가 있으며, 실제로 이번 세션에서 "DB를 잃으면 워커 fleet 전체를 수동
재발급해야 한다"는 결함을 발견했다. 그런 상황에서 복구 순서를 담은 계획이 같은 DB에 있으면 안 된다.
Model C는 생성된 파일이 git에 남으므로 이 위험이 없다.

**Model B는 관측된 문제를 하나도 풀지 않는다.** 회귀 3회의 원인인 파일 편집이 그대로 남는다.
Agent claim만 얻고 나머지는 유지되므로, "지금은 이걸로 두고 나중에" 하는 선택지로서만 의미가 있다.

## 5. 권고

**Model C.** 단, 한 번에 가지 않는다.

1. **`#88`·`#93`을 Model B 형태로 먼저 구현한다.** 트래커는 실무 단위부터 다루고 roadmap.md는
   손으로 유지한다. 부트스트랩 공백을 정직하게 인정하는 단계다.
2. 트래커가 실제 사용되어 스키마가 안정되면, roadmap 행 스키마(ID·항목·우선순위/상태·정본
   링크·완료 게이트·선행 조건)를 Issue의 필드로 표현할 수 있는지 검증한다. 특히 **정본 링크를
   필수 필드로** 만들어 `이 행` 관행을 끊는다.
3. 렌더러를 만들고 roadmap.md를 생성물로 전환한다. 절 산문은 별도 입력으로 분리한다.
4. 보존 레지스트리(`#1`~`#47`)는 스키마가 다르고 변경되지 않으므로 **이주하지 않고 그대로 둔다.**
   역사 기록이며 조회 대상이 아니다.

이 순서면 각 단계가 독립적으로 가치를 내고, 어느 단계에서 멈춰도 상태가 일관된다.

## 6. 결정되지 않은 것

- 렌더링 시점(커밋 훅, CI, 수동 명령)과 생성 파일이 DB와 어긋났을 때의 판정
- 절 산문의 입력 형식
- Agent가 계획 항목(`#N`)까지 claim할 수 있는가 — 실무 단위만 claim하고 계획 항목은 사람이
  분해하는 편이 안전해 보이나, 3단계 이후에 다시 판단한다
