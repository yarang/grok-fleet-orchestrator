# 구현 로드맵

이 문서는 승인된 설계를 어떤 순서로 구현할지, 각 작업의 상태와 완료 게이트가 무엇인지 관리한다.
시스템 동작과 계약의 정본은 각 Architecture·Security·Contracts 문서이며, 이 문서는 설계를
재서술하지 않는다. 상태와 ID 규칙은 [Roadmap 도메인 안내](README.md)를 따른다.

## 현재 구현 순서

각 단계는 이전 단계의 정상·실패 경로 검증을 통과한 뒤에만 활성화한다. 신규 Agent/Project 기능은
direct-worker Task 경로를 대체하지 않고 feature flag 뒤에서 점진적으로 도입한다.

| 단계 | 배포 가능한 increment | 포함 Roadmap ID | 우선순위 | 활성화 게이트 |
|---:|---|---|---|---|
| 0 | production trust foundation | #58, #59 | P1 | no-auth fail-closed, endpoint/tool authorization matrix, bootstrap 원문 DB 부재 |
| 1 | Worker identity와 credential authority | #60, #66, #55 | P1 | mTLS/self binding, Security Manager delivery grant, raw export 비활성화 |
| 2 | 실행 일관성과 제어 권한 | #62, #63, #61 | P1 | Task 상태 CAS, control epoch fencing, inventory-first recovery, bounded control channel |
| 3 | durable workspace와 공유 Host 안전성 | #69, #64 | P1 | Git checkpoint 복구, container isolation, privileged helper 거절 경로 |
| 4 | 최소 Project·Agent lifecycle | #48, #67, #49 | P2 | Project scope, one Agent/one Attempt, Hibernated E2E; WarmIdle 비활성 |
| 5 | 운영 완결성 | #68, #70, #65, #50 | P1~P2 | archive hold, reconciliation/alert, reproducible skill, attach security gate |
| 6 | 확장 기능 | #51, #52, #53, #54, #56 | P2 | 앞 단계 불변식 유지와 vendor/gateway 회귀 검증 |

**첫 착수 단위**는 #58의 `AuthorizationContext`/fail-closed middleware와 #59의 bootstrap digest
migration이다. 이 단계가 완료되기 전에는 Project/Agent control API, Security Manager delivery API,
MCP mutation 확장을 외부에 노출하지 않는다.

P1은 프로덕션 보안과 실행 신뢰성 게이트다. P2 기능 확장은 관련 P1 불변식을 우회하지 않는
범위에서만 병행한다. 긴급 credential 폐기·재발급 같은 사고 대응은 이 순서보다 우선한다.

관측이 아니라 **결정**이고 4a에는 옮길 프로세스가 없다 — 인라인이라 감사 actor가 실재하는 사람이며 두 오케스트레이터가 같은 행을 두고 경합할 경로가 없어 `lease_allows_control()` 게이트도 불필요하다), `unassign_agent_worker`(원장이 `status <> 'stopped'`만 세므로 회수가 자리를 자동으로 `workers.circuit_state` 컬럼이라 **레지스트리보다 한 번의 쓰기만큼 뒤진다**(Dashboard의 `DashboardState`에는 `FleetState`가 없어 강제된 선택이며, `Store::update_worker_circuit_state`가 no-op 기본 구현이라 MemStore 테스트는 `Worker::circuit_state`를 직접 세팅한다). (2) 원장을 읽고 INSERT하기까지가 **원자적이지 않다** — 동시에 두 Agent를 만들면 같은 Worker를 고를 수 있다. 상한이 없는 4a에서는 부하 분포가 잠시 기우는 것으로 끝나지만 상한이 생기는 순간 초과 배정이 되므로, CAS slot claim을 구현 게이트 ①로 남긴다. 부수 수정 둘: `MemStore::assign_agent_worker`가 존재하지 않는 Worker를 `Conflict`로 거절하도록 PgStore의 FK를 미러링했고(미러링하지 않으면 400 경로를 검증하려던 상위 테스트가 성공 경로를 밟고도 초록이 된다 — 판정 **순서**까지 맞췄다: PgStore의 UPDATE는 Agent가 없으면 0행을 갱신하고 FK에 닿지도 않으므로 둘 다 없을 때의 답은 `Ok(false)`(→ 404)이지 FK 위반이 아니다), `#agent-table`에 `grid-template-columns`를 신설했다(`#49` 1단계 때부터 전용 규칙이 없어 데스크톱에서도 세로로 쌓여 있었다 — `#activity-table` 묶음과 같은 누락) **4b(이번): 수렴 프로토콜 — 명령을 큐가 아니라 상태로 나른다.** `agents` 행에 `desired_status`·`command_generation`·`last_acked_generation` 세 컬럼을 얹고(`031_agent_desired_state.sql`, `CHECK (last_acked_generation <= command_generation)`), heartbeat 응답이 매 박동마다 그 Worker에 배정된 Agent 명령 **전체 목록**을 다시 싣는다. Worker는 같은 세대로 ACK하고, 저장소는 `WHERE command_generation = $ack AND worker_id = $worker AND last_acked_generation < $ack` CAS로만 그것을 받는다 — 이 술어 하나로 "지연된 ACK가 이미 추월당한 명령을 확인해 주지 못한다"와 "소유하지 않는 Worker의 ACK는 거부된다"가 공짜로 따라오고, 큐 설계였다면 필요했을 `expires_at`이 사라진다(신선도의 판정이 시각이 아니라 세대이기 때문이다). **발행 지점은 명시적 start 표면 하나뿐이다** — 생성도 배정도 아니다. 4a가 생성 시점에 자동 배정하므로 "배정 ⇒ running"은 곧 "생성 ⇒ running"이 되고, 그러면 `AgentStatus::Ready`의 정의("정의는 끝났고 시작 명령을 받을 수 있다")가 빈 말이 된다. 표면은 `POST /api/agents/{id}/start`와 `fleet_start_agent` 둘이며 `agent:manage`를 요구하고, 값이 실제로 바뀔 때만 세대를 올리고 `agent.start` 감사 이벤트를 남긴다(같은 의도를 다시 눌러도 이벤트가 늘지 않아야 "몇 번 시작을 명령했나"가 뜻을 갖는다). 경계 둘: `stopped`는 종단이라 **핸들러에서** 거절하고(UPDATE 술어에 `status <> 'stopped'`를 넣으면 "안 바뀜"과 "그런 Agent 없음"이 0행으로 합쳐져 400과 404를 나눌 수 없다), 미배정 Agent는 **허용한다**(다음 배정이 세대를 올리며 명령을 실어 간다). 회수 명령은 ACK될 때까지 목록에 남는다 — 술어가 `status <> 'stopped' OR last_acked_generation < command_generation`인 이유이며, OR의 오른쪽이 없으면 정지 때 올린 세대가 **영원히 전달 불가능**해져 그 Agent의 `command_delivered()`가 영구히 false가 된다. `Starting`은 컬럼이 아니라 `(status, desired_status)`의 순수 함수(`Agent::is_starting()`)라 `027`의 CHECK를 건드리지 않는다. `HeartbeatResponse.agents`가 `Vec`이 아니라 `Option<Vec>`인 것도 의도다 — `None`은 "이번 박동에 권위 있는 목록이 없다(저장소 실패 또는 구버전 오케스트레이터)"라서 아무것도 바꾸지 않고, `Some([])`만 "정말로 없다"다. 맨 `Vec`이었다면 저장소 오류 한 번이 4c가 붙는 순간 전 함대 종료 신호가 된다. **검증 한계**: 이 단계가 증명하는 것은 의도의 기록과 **전달**까지이며, `last_acked_generation == command_generation`은 수렴이 아니라 수신 확인이다. 프로세스가 실제로 떴는지는 관측 주체가 생기는 4c 이후에만 말할 수 있고, ACK를 보내는 Worker측 처리도 4c에 있다 — 지금 Worker는 목록을 파싱만 한다. **4c-A: 워커측 프로세스 매니저 — 명령이 처음으로 프로세스를 움직인다.** `crates/fleet-worker/src/agent_process.rs`의 `AgentProcessManager`가 heartbeat 응답의 `agents` 목록으로 자기 프로세스 집합을 수렴시킨다. **4c를 4c-A/4c-B로 다시 나눈 기준은 마이그레이션 경계다** — `Starting`/`Running`/`Failed`를 관측 상태로 실으려면 `027`의 `status IN ('ready','stopped')` CHECK를 넓혀야 하고, 그러려면 그 값들의 생산자(매니저)와 `agents` 행까지의 경로(ACK 확장·store·표면 3종)가 **한 커밋에** 있어야 한다. 아니면 아무도 만들지 않는 enum variant가 생기며, 그 대가는 `#70`이 죽은 `FailureKind` 3종을 제거하며 이미 치렀다. 그래서 4c-A는 마이그레이션을 만들지 않고, 4c-B가 CHECK 확장·관측 상태·관측을 싣는 ACK·`is_starting`→`start_pending` 개명을 한 번에 한다. **매니저는 `GrokRunner`를 대체하지 않고 옆에 선다** — singleton은 `workers.endpoint`로 등록된 이 Worker의 ACP 종단이고 모든 Task dispatch가 그리로 가므로, Agent별로 쪼개면 `tasks.agent_id` 라우팅(`#49` 2단계)이 생기기 전까지 dispatch가 갈 곳을 잃는다. **포트·secret·cwd는 워커 로컬 파생이다** — 4b가 명령 페이로드를 `(agent_id, desired_status, generation)`으로 못박았으므로 오케스트레이터는 이 값들을 모른다. 포트는 `grok.agent_port_range`(기본 `2420-2519`, singleton 기본 포트 `2419` 바로 다음이라 겹치지 않음이 값만 보고 확인된다)에서, cwd는 `agent_workspace_root/<agent_id>`(기본 `<cwd>/fleet-agents`)에서, secret은 **Agent마다 새로** `hex(rand 32B)`로 만든다 — `grok.secret` 재사용은 그 값이 이미 Worker 종단을 여는 열쇠라서 금지다. **거절 경로는 하나다** — 포트 소진과 `max_agent_processes`(기본 4) 초과는 원인이 다르지만 결과("이번 beat에 뜨지 않았다")가 같고 4c-B에서 같은 상태로 접히므로, 이름을 둘로 나누면 운영자가 서로 다른 두 오류에 같은 처방을 찾게 된다. 한 자리에서 거절하고 원인은 로그 필드로 구분한다. `reconcile`은 **죽은 자식 수거를 맨 앞에** 두어 "desired=running인데 없으면 띄운다"가 재기동을 겸하게 했다 — 별도 재시작 경로를 만들면 상한 검사가 두 곳으로 갈라진다. 정리는 `terminate_all`로 **동시에** 돌린다: `terminate_child`는 이름과 달리 SIGTERM을 보내지 않고(이 크레이트는 `#![forbid(unsafe_code)]`이고 `nix`가 의존성에 없다) 5초를 항상 다 쓰므로, 직렬이면 상한 4개에 20초가 걸리고 그동안 lock을 쥔 채 heartbeat 간격(15초)을 넘겨 beat을 통째로 건너뛴다. **`Option<Vec>`이 여기서 처음 하중을 받는다** — `None`은 아무것도 바꾸지 않고 `Some([])`만 전부 정리하며, 테스트가 이 둘을 반드시 구분해서 확인한다. 신규 테스트 12건(`agent_process`, 가짜 grok 스크립트로 프로세스 수명만 시험). **의도적으로 만들지 않은 것**: Agent `Draining`, Worker `drain`의 Agent 명령 억제, 백그라운드 reconciler, `on_demand` Worker에서의 수렴(그 Worker는 heartbeat 루프 자체를 시작하지 않고 4a의 배치 선택기가 이미 후보에서 제외한다). **검증 한계**: 오케스트레이터는 여전히 **전달**까지만 안다 — 프로세스가 실제로 떴다는 사실은 워커 로그에만 남고, 관측 상태를 실어 보낼 채널은 4c-B다. 즉 4c-A에서 거절은 **조용한 실패**다. `free_port`의 bind 프로브와 자식의 실제 bind 사이에는 TOCTOU 창이 남는다(자식에게 소켓을 물려주려면 `grok agent serve`에 그 인터페이스가 있어야 한다). 포트 소진·상한 거절과 4a 원장의 불일치(원장은 "배정됐다"고 세고 Worker는 "못 띄운다"고 본다)는 4a가 이미 게이트 ①로 미뤄 둔 CAS slot claim과 **같은 창**이다. 이 12건은 전부 가짜 grok 스크립트를 상대로 한 것이며, 실제 `grok agent serve`를 여럿 띄워 본 적은 없다. **4c-B(이번): 관측이 오케스트레이터에 도달한다.** 새 마이그레이션 `032_agent_observed_state.sql`이 `agents`에 `observed_status`(`running`·`failed`)·`observed_at`·`observed_reason`(`cap_reached`·`no_free_port`·`spawn_failed`) 셋과 세 값의 조합을 강제하는 CHECK `agents_observation_complete`를 더한다. Worker의 `reconcile`이 관측 목록을 돌려주고, 다음 beat의 heartbeat 요청이 `agent_observations`로 실어 보내며, `Store::apply_agent_observations`가 적용한다. 표면 셋(Dashboard `AgentSummary`, MCP `agent_json`, store)이 그 값을 노출한다. **`027`의 `status` CHECK를 넓히지 않은 것이 이 단계의 핵심 판단이다** — 넓혔다면 한 컬럼에 두 명이 쓰게 되어, 회수(`stopped`)가 그 회수를 보기 전에 만들어진 heartbeat(`running`)에 덮여 **조용히 취소된다**. 컬럼을 나누면 `AgentStatus::blocks_project_archive()`가 손대지 않고도 계속 옳다는 것이 축이 실제로 다르다는 방증이다. `031`의 마이그레이션 주석이 이미 같은 결론을 적어 뒀다. **생산자가 있는 값만 만들었다**: 상태 기계표가 정의한 관측 `Starting`은 만들지 않았다(4c-A에 health check가 없어 `try_wait()`는 "죽지 않았다"만 말한다), `exited`도 만들지 않았다(`reconcile`이 0단계에서 거두고 3단계에서 **같은 beat에** 다시 띄우므로 정직한 관측은 `running`이다). 대신 어휘에 없던 세 번째 생산자 `spawn_failed`(`cmd.spawn()`의 `Err`)를 찾아 넣었다. 요청 필드는 `Vec`이 아니라 `Option<Vec>`이다 — 목록이 **권위 있는 전체 집합**이라 `[]`가 "남은 관측을 전부 지워라"이고, 필드 부재가 "모른다"이기 때문이다. 접었다면 마지막 Agent를 회수한 뒤 그 관측을 지울 사람이 영영 없어진다(타입이 잡지 못해 `api_flow.rs`가 선 위에서 단정한다). `is_starting` → `start_pending` 개명은 예정대로 했으나 **사유는 예정과 다르다** — 이름 충돌(관측 `Starting`)은 그 variant를 만들지 않아 일어나지 않았고, 실제 이유는 술어에 `observed_status.is_none()` 항이 붙어 뜻이 "명령은 냈고 답이 없다"로 바뀐 것이다. 이 항을 빠뜨렸다면 돌고 있는 Agent가 영원히 "시작 중"으로 보고되는데 컴파일러도 4b의 기존 테스트도 그것을 잡지 못한다(새 컬럼을 모르기 때문). 그래서 `observation_clears_start_pending`이 항이 사라지면 깨지도록 지킨다. **검증 한계**: crash loop은 보이지 않는다 — 0단계 수거와 3단계 재기동이 같은 beat에 일어나 매 beat 죽는 Agent도 `running`으로 관측된다. 드러내려면 상태가 아니라 **사건**(재기동 횟수·전이)이 필요하고 그 채널도 소비자도 없다. `max_agent_processes` 신고는 4c-B 시점에는 읽을 소비자가 없어 만들지 않았는데, **게이트 ①-A-1이 그 소비자를 만들면서 사유가 만료됐다** — 아래에 이어 쓴다. 실 프로세스 검증은 여전히 가짜 grok 스크립트 상대다.<br><br>**구현 게이트 ①-A-1(이번): Worker가 신고한 Agent 프로세스 상한이 배정 후보를 필터한다.** 게이트 ①("배정 초과·낡은 제어면 없음")은 한 덩어리로 닫을 수 없어 ①-A(배정 초과)와 ①-B(낡은 제어면)로 나눴다. ①-B는 lease 레코드가 `task_id`를 담는데 그 값을 채우려면 dispatch가 Agent를 고를 수 있어야 해서(`#49` 2단계) 지금 만들면 항상 NULL인 컬럼이 된다 — 그래서 막혀 있다. ①-A는 lease 테이블을 필요로 하지 않는다: 세어야 하는 것이 lease 행이 아니라 **배정된 `agents` 행**이기 때문이다. 그 ①-A를 다시 둘로 쪼갰다. ①-A-1은 상한이 오케스트레이터까지 **도착**해서 후보를 거르는 데까지, ①-A-2는 그 판정을 `workers` 행 잠금 아래로 옮겨 **불변식을 세우는** 데까지다. 순서는 편의가 아니라 데이터 의존이다 — ①-A-1이 없으면 ①-A-2가 잠금 아래에서 셀 숫자 자체가 존재하지 않는다.<br><br>이번에 만든 것: `workers.max_agent_processes`(migration 031이 아니라 **033**), `RegisterRequest`/`WorkerSummary`의 같은 이름 필드, `fleet-worker`의 register 페이로드, 그리고 `choose_worker`가 부하 정렬 **앞에** 거는 후보 필터와 `PlacementError::AllAtCapacity`. 컬럼은 **nullable이고 DEFAULT가 없다**. `max_concurrent`처럼 `NOT NULL DEFAULT 4`를 두면 실제 상한이 2인 구버전 Worker에 대해 4라고 **적어 두는 것**이 되는데, 그것은 모르는 값을 아는 값으로 날조하는 것이다. `None`은 "상한이 없다"가 아니라 "이 Worker의 상한을 **모른다**"이고, 모르는 상한은 필터하지 않는다. 이 관대함이 정당한 이유는 오케스트레이터의 상한이 유일한 방어선이 아니라 **두 번째**이기 때문이다 — 집행은 Worker의 `agent_process.rs`가 하고, 초과 시 `observed_reason='cap_reached'`로 되돌려 준다. 반대로 "모르면 배정하지 않는다"로 두면 구버전 Worker만 있는 fleet에서 배정이 통째로 멈추는데, 그쪽이 훨씬 나쁜 고장이다.<br><br>join은 이 값을 싣지 않는다 — 그 시점에는 `worker.toml`이 아직 상한 Worker는 필터를 통과하고, 무엇보다 두 수가 **세는 대상이 다르다** — 오케스트레이터는 배정된 행을, 워커는 살아 있는 프로세스를 센다. **검증 한계**: ①-A-1은 읽은 시점의 수로 판정하므로 동시 요청 둘이 같은 빈자리를 함께 통과할 수 있다. 불변식이 서는 것은 ①-A-2부터이며, 그래서 [권한과 장애 전환](../architecture/control-plane-authority-and-failover.md)의 동시 slot claim 행은 그 커밋에서는 **미착수**로 두었다.<br><br>**①-A-2(2026-09-01): 선점을 `workers` 행 잠금 아래로 옮겨 불변식을 세웠다.** `INSERT ... WHERE (SELECT COUNT(*) ...) < cap`은 READ COMMITTED에서 전형적인 phantom이다 — 두 트랜잭션이 같은 수를 읽고 둘 다 통과하며, 세는 대상(`agents`)에 **아직 존재하지 않는 행**은 잠글 수도 없다. 그래서 잠그는 것은 세는 대상이 아니라 **상한의 주인**이다: `SELECT max_agent_processes FROM workers WHERE id = $1 FOR UPDATE` 아래에서 다시 세고 조건부로 쓴다(`PgStore::create_agent`와 `assign_agent_worker` 둘 다). 잠금이 Worker별이라 서로 다른 Worker로 가는 배정은 그대로 병렬이다. READ COMMITTED이 전제다 — 문마다 새 스냅샷을 뜨므로 대기자가 승자의 커밋된 행을 본다.<br><br>**반환형을 넓힌 것이 이번 변경의 절반이다.** `assign_agent_worker`는 `bool` 대신 `SlotClaim::{Claimed, CapReached, NoSuchAgent, NoSuchWorker}`를 돌린다 — 실패가 두 가지 **다른 사실**이기 때문이다(상한은 지금의 fleet 상태라 409이고 나중엔 되지만, 없는 대상은 요청의 결함이라 404/400이고 다시 해도 같다). MCP의 배정 경로는 이전에 `bool`을 통째로 버려서 **존재하지 않는 Agent가 조용히 성공**했는데 그것도 여기서 닫혔다. `create_agent`는 `Result<Option<WorkerId>, StoreError>`로 **실제로 기록된 배정**을 돌려주고 호출부가 로컬 구조체를 되맞춘다(`Agent::without_placement()`). 조용히 강등하면 응답뿐 아니라 **감사 로그**가 일어나지 않은 배정을 기록하는데, 응답의 거짓은 다시 조회하면 드러나지만 감사 로그의 거짓은 남는다.<br><br>세부 두 가지. (1) 재배정 카운트에 `AND id <> $agent_id`를 붙인다 — 이미 그 Worker에 있는 Agent를 같은 Worker로 다시 배정하는 것은 슬롯을 추가로 쓰지 않으므로, 자기 제외가 없으면 정확히 가득 찬 Worker에서 무해한 no-op이 거절된다. (2) 잠금 순서를 `workers → agents` 하나로 고정한다. Postgres 쪽 Agent 존재 확인을 일부러 **잠그지 않고** 읽는 이유가 그것이고, MemStore에서는 이것이 권고가 아니라 강제다 — Mutex를 반대 순서로 잡으면 곧바로 데드락이다.<br><br>**검증**: 잠금은 `create_agent`와 `assign_agent_worker`에 **따로** 걸려 있으므로 붉은 증명도 둘이다. `concurrent_creates_cannot_exceed_the_cap`(생성)과 `concurrent_placements_cannot_exceed_the_cap`(재배정)이 각각 상한 1인 Worker에 8-way 배리어 경합을 걸어 `(Claimed, CapReached) == (1, 7)`과 저장된 행 수 1을 함께 단정한다. **테스트가 자기 하네스에 속을 수 있다 — 풀은 크기를 정하는 것으로 부족하고 미리 채워야 한다.** 하네스 기본 풀(4 커넥션)로는 체크아웃에서 직렬화되어 `FOR UPDATE` 없이도 통과하는데, `max_connections(8)`로 올리는 것만으로는 그 직렬화가 한 겹 아래로 옮겨갈 뿐이다 — sqlx의 `connect()`는 커넥션을 하나만 열고 `min_connections` 기본값은 0이라 Barrier가 풀린 뒤 나머지를 **접속하는** 비용이 출발선을 흩는다(실효 동시성 2). `min_connections`도 백그라운드 채움이라 보장이 아니고, 유일한 보장은 커넥션 N개를 직접 `acquire()`했다 버리는 것이다(`race_pool()`). 그 전후로 잠금 없는 코드의 실패값이 `left: (2, 6)` → `left: (8, 0)`으로 바뀐다 — 8개 **전부**가 상한 1인 Worker에 앉는다. **붉은 값이 6회 내내 흔들리지 않은 것은 안심할 근거가 아니라 하네스 결함의 단서였다**: 초안은 그것을 "phantom 창이 좁다"로 읽었지만 실제로는 하네스가 동시성을 2로 묶고 있었고, 그 상태로는 기계가 조금만 달라도 잠금 ## 갱신 시점

- 요구 승인 시 ID, 독자 가치, 우선순위와 책임 문서를 등록한다.
- 설계 승인 시 정본 링크, 구현 단계, 선행 조건과 검증 가능한 완료 게이트를 확정한다.
- 구현 착수 시 `구현 중`, 코드·테스트·운영 문서가 게이트를 충족하면 `완료`로 바꾼다.
- 계약이나 범위 변경은 설계 정본을 먼저 수정한 뒤 이 문서의 순서·게이트만 동기화한다.
- 폐기하거나 강등해도 ID는 삭제·재사용하지 않고 한 줄 종결 기록을 남긴다.

특정 시점의 테스트 개수, 상세 회고와 설계 개정 횟수는 누적하지 않는다. 현재 사실은 CI와 코드,
변경 경위는 Git 이력과 필요한 경우 `docs/reviews/`가 담당한다.
